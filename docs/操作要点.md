# 操作要点

做旅行订单时直接照这里执行。规则在 [`铁律.md`](铁律.md)，交付前检查用 [`质检清单.md`](质检清单.md)。

---

## 框架阶段：先把闭馆日排开，再排景点

**同城多个博物馆时，闭馆日往往互相咬死，可行排法只有一种。** 先列一张矩阵再动手。

巴黎实例（客户住 4 天，要卢浮宫、凡尔赛、奥赛、迪士尼）：

| | 周日 | 周一 | 周二 | 周三 |
|---|---|---|---|---|
| 卢浮宫 | ✅ **去** | ✅ | ❌闭馆 | ✅ |
| 橘园 | ✅ **去** | ✅ | ❌闭馆 | ✅ |
| 凡尔赛 | ✅ | ❌闭馆 | ✅ **去** | ✅ |
| 奥赛 | ✅ | ❌闭馆 | ✅ | ✅ **去** |
| 迪士尼 | ✅ | ✅ **去** | ✅ | ✅ |

**把每日开放的项目（迪士尼、主题乐园、露天景点）放在闭馆最多的那天**，等于把最差的一天用掉。上表周一有三个馆同时闭馆，迪士尼放这天正好。

常见闭馆日：卢浮宫周二、奥赛周一、凡尔赛周一、橘园周二、佛罗伦萨乌菲兹与学院周一、罗马博尔盖塞周一、圣天使堡周一、梵蒂冈博物馆周日、曼彻斯特赖兰兹图书馆只开周三至周六、剑桥菲茨威廉周一、约克大教堂周日只开 12:45–15:15。

## 选模板

**同一城市有多个版本时，选图片最多的那一版。** 图片多的是最近做的新模板，机位和备注都补齐了；图片少的是早期草稿。

```bash
python3 tools/取路线.py --list 罗马
```

```
ROM-R03-A    图 10  西班牙阶梯＋许愿池＋万神殿线      ← 用这个
ROM-R02      图  5  斗兽场＋古罗马广场＋南线
ROM-R01      图  2  抵达罗马｜FCO落地至Termini      ← 早期版本，别用
```

**先按内容筛，再按图片数排。** 客户说"入内只去乌菲兹"，就先排除含学院美术馆的版本，再在剩下的里挑图最多的。

## 客户在一城住几天，就用对应的"几天"套装

模板文件内部分了「一天／两天／三天」的节，同一节里的表是配套的，景点已经分配好。**住两晚就用两天版，不要拿一天版拆成两天**——那样第一天会塞爆、第二天没内容。

| 模板文件 | 住 1 晚 | 住 2 晚 | 住 3 晚 |
|---|---|---|---|
| 佛罗伦萨通用 | `FLR-R02` 或 `FLR-R03` | **`FLR-R01`（乌菲兹）+ `FLR-R04`（皮蒂宫＋波波里）** | — |
| 罗马通用 | `ROM-R03-A` | `ROM-R04-A` + `ROM-R04-B` | — |
| 爱丁堡两天通用版本 | `EDI-R03` | `EDI-R01` + `EDI-R02` | — |
| 巴黎行程通用计划 | — | `PAR-R03-A` + `PAR-R02` | `PAR-R05-A` 起 |
| 伦敦通用模板 | `LON-R03-C` | `LON-R01-A` + `LON-R02-A` | `LON-R05` + `LON-R03-C` + `LON-R01-B` |
| 柏林两天 | — | `BER-R02` + `BER-R03`（抵达日另加 `BER-R01`） | — |
| 慕尼黑三天 | `MUC-R01` | — | `MUC-R01` + `MUC-R02` + `MUC-R04` |
| 巴塞罗那＋Tossa 3天 | `BCN-R01` | `BCN-R01` + `BCN-R02` | `BCN-R01` + `BCN-R02` + `BCN-R03` |

分节标题在 DOCX 里是普通段落，Ctrl+F 搜「两天」「3天」能看到。

## 客户已定的票，倒推整天

拿到票的确切时段后，**整天围着它重排**，不要沿用模板原来的顺序。

实例：梵蒂冈博物馆定了 12:30（下午场），模板默认是 8:00 早场。改成上午先去圣彼得大教堂（8:00 开门就到，避开它 1 小时起的排队），11:00 提前吃午餐，12:15 到入口报到。

实例：斗兽场定了 13:45，模板默认上午。整天倒过来——上午安排博尔盖塞和万神殿区，午餐压到 45 分钟，13:30 到场排安检。

**票的场次是硬锚点，模板的时间只是参考。**

## 客户对某天的特殊要求，优先级高于模板

比如"23 号上午不安排行程""奥赛和凡尔赛放同一天""入内只去乌菲兹，没写的不写入内"。

这类要求直接决定选哪个版本的模板——客户说入内只去乌菲兹，就要选不含学院美术馆的版本，哪怕它图更少。

## 转场版模板用在非转场日，删掉后半段

很多模板是"某城最后一天＋转场去下一城"的合体。客户当天不走时，把取行李、候车、火车、抵达下一城、下一城晚餐这些行整段删掉，再补当天下午和晚上的内容。

这类模板：`FLR-R04`（转威尼斯，后半 7 行要删）、`VCE-R03`、`LUC-R04`、`PSA-R01`、`BIC-R01`。

## 每一天都从起点写起，写到回酒店

**不要从第一个景点开始写。** 每天的第一行必须是当天的起点，最后一行是回酒店。

| 这一天的类型 | 第一行写什么 |
|---|---|
| 落地日 | 航班落地（写航班号、航站楼、几点）→ 入境／取行李 → 怎么进城 → 酒店寄存或入住 |
| 转场日 | 酒店退房 → 怎么去车站／机场 → 值机安检 → 车次／航班 → 抵达 → 怎么到下一个酒店 |
| 平常日 | 酒店出发 → 怎么到第一个景点（地铁几号线、哪站、走多久） |

**中间每一段移动都要写清楚怎么走**：交通方式、耗时、票价、在哪上车哪下车。景点与景点之间不要直接跳。

**每天最后要写回酒店**，并在备注里带上"明天要注意什么"（几点出发、哪张票要带护照、今晚要整理行李）。

## 保姆级到什么程度

一段交通要写到客户不用再查任何东西：

```
09:15 - 10:00　机场 T1 → 市区　　Aerobús A1
● Aerobús A1 从 T1 直发加泰罗尼亚广场，约 35 分钟，单程约 €7.25，可放大件行李
● 备选地铁 L9S：需在 Zona Universitària 换乘，机场段约 €5.5，不能用 T-casual 10 次票
● 备选出租车：约 €35–40，30–40 分钟
```

**同一段路给 2–3 种方式**，各写价格和耗时，让客户自己挑。

机场段还要写：走哪个指示牌、在哪买票、票怎么激活、公务舱能不能走快速通道、申根内部航班有没有边检。

## 做逐日行程：用 拼行程.py 搬表，不要自己打

```bash
python3 tools/拼行程.py 配方.json 输出.docx
```

**不要重新录入模板内容。** 重打会丢掉模板里所有图片、字体、列宽和 `●` 分点格式——实测一份 9 天行程重打后图片数为 0，模板里原本有 42 张。

配方写法见 `tools/README.md`，完整示例见 `tools/配方示例.json`。

---

## 改表格用行级操作，不要用字符串替换

配方里用 `删` / `改` / `增` / `序` 四种操作。字符串 `替换` 只用于备注里的零散措辞（比如把"5 月"改成"9 月"）。

原因：Word 会把一句话拆进多个 run，跨 run 的字符串匹配不上，经常整天 0 处生效；而且字符串替换改不了行的增删和顺序。

---

## 定位关键词要唯一

`改` 和 `删` 默认只匹配「行程内容」列。以下情况会误伤：

- **一个词命中多行**：`万神殿` 会同时命中「万神殿（内部参观）」和「午餐（万神殿附近）」。改用 `（内部参观）`。
- **备注里提到别的景点**：古罗马广场那行的备注写着"从后门6出口出去就是真理之口"。默认只匹配行程内容列已经避开，但用 `整行匹配` 时要注意。
- **包含关系**：`波波里花园` 会命中「皮蒂宫 → 波波里花园」。用 `"精确": true` 做整格全等匹配。
- **行程内容相同、只有交通不同**：三行都是"机场→Termini"，区别在 Leonardo Express／出租车／机场大巴。用 `"配列": "交通"` 指定按交通列匹配。

---

## 纵向合并的时间格，一次写全

模板里常有两行共用一个「时间段」格，比如"剪影机位"和"米开朗基罗广场看日落"。对这两行分别写时间，只有一次生效。

直接写 `19:00 - 20:15` 覆盖两行，不要分别写 `19:00-19:15` 和 `19:15-20:15`。

---

## 这四类变量每次都要换

模板里留的是上一位客户的数据，逐条替换，不要只改标题：

| 类型 | 模板里可能留着的 | 怎么处理 |
|---|---|---|
| **旧客户行程** | 首行"佛罗伦萨→罗马"、"酒店寄存行李"、上一单的出发城市 | 整行删掉或改成本单的来向 |
| **具体日期** | "9月18日是周五，正常开放"、西班牙段的"2月8日–2月14日" | 换成本单日期，并按新日期重查开放时间 |
| **日落时间** | "8月日落约20:20-20:30"、"6月罗马日落20:45" | 按客户月份重算，日落决定傍晚整段的时刻 |
| **季节描述** | "5月海水微凉"、"5月阳光下外墙最亮眼"、"5月闭园19:30" | 换成客户月份的实际情况 |
| **班次时刻** | 模板里精确到分钟的车次、船班、大巴 | 按客户日期在官方 App 重查，模板时刻只是参考 |

## 出稿后逐行核对

`拼行程.py` 会自动查三项：时间倒流、时段完全重复、旧客户信息残留。

工具查不出来的要人眼过：

1. **每天第一行是不是起点** —— 落地日有没有写落地和进城，平常日有没有写从酒店出发
2. **段与段之间有没有断层** —— 两个景点之间有没有写怎么过去
3. **整段缺失** —— 比如抵达日没有取行李、进城、入住的行
4. **来源城市不对** —— 首行还写着上一位客户的出发城市
5. **入内项目不符** —— 客户说只进乌菲兹，却排了学院美术馆
6. **日落和季节描述改了没** —— 模板里常留着别的月份
7. **每天最后有没有回酒店**

把每天的时间段和行程内容打印出来看一遍，再说做完了。

## 交付格式

**最终交付一律是 DOCX，字体 HYJunHei-EEJ、字号小五。** 不要给 `.md`——Markdown 的竖线在文本编辑器和 WPS 里就是一串 `|`，没法用。Markdown 和 JSON 只用于中间处理。

交付前核对图片数与模板一致，为 0 说明内容被重打了。

---

## 判断文件是模板还是成品

看内容里有没有客户特定信息——**具体日期、人数、航班号、酒店名**。有就是成品，没有就是模板。文件放在哪个目录不改变它的性质。

成品不能当模板用，会把上一位客户的日期和人数带进新订单。

---

## 能直接做的事就做完

本地文件改名、移动、整理，直接做完再说明改了什么，不要写成待办交回去。

自有仓库的提交推送、生成文件，属于常规操作，做完汇报即可。

删除、覆盖、推送到别人的仓库这类不可逆或对外的操作，先问。

---

## 规则只写进铁律

新增规则写进 [`铁律.md`](铁律.md)，其他文档引用、不复述。同一条规则写在多个文件里，改一处就会漏掉其他处。

## 客户沟通不是 AI 的活

交付 SOP 第一步（需求收集）和第三步（客户确认）由负责人做。仓库不存沟通话术。
